# Драйверы

## Постановка проблемы: зачем нужны драйверы

### Общая характеристика

Операционная система управляет множеством аппаратных устройств: дисками, сетевыми картами, клавиатурами, мониторами,
USB-устройствами. Каждое из этих устройств имеет собственный набор команд, регистров и протоколов взаимодействия.

Ключевая идея:

> Операционная система не может знать заранее, какое оборудование будет подключено к компьютеру и как с ним работать.

---

### Проблема разнообразия оборудования

Рассмотрим конкретный пример. Для того чтобы записать данные на диск, операционная система должна:

* знать тип интерфейса (SATA, NVMe, USB)
* знать протокол команд (ATA, SCSI, UAS)
* знать порядок передачи байтов
* уметь обрабатывать ошибки устройства

Для каждой модели устройства эти детали различны.

Следствие:

> Если бы ОС работала с каждым устройством напрямую, ядро превратилось бы в хаотичный набор специфичного кода для
> каждого производителя.

---

### Решение: слой абстракции

Операционная система решает эту проблему через введение **драйвера устройства**.

Драйвер — это программный компонент, который:

* знает как работать с конкретным устройством
* предоставляет ОС стандартный интерфейс
* скрывает детали реализации оборудования

Структура взаимодействия:

```text
Приложение
↓
Операционная система (стандартный интерфейс)
↓
Драйвер (специфичный код для устройства)
↓
Устройство
```

Ключевой вывод:

> Драйвер — это переводчик между языком операционной системы и языком конкретного устройства.

---


* для каждого устройства в системе существует драйвер

## Место драйвера в архитектуре операционной системы

### Напоминание: user space и kernel space

Операционная система разделяет всё программное обеспечение на два уровня:

**User space** — пространство пользователя:

* приложения
* системные библиотеки
* ограниченный доступ к ресурсам

**Kernel space** — пространство ядра:

* ядро операционной системы
* полный доступ к оборудованию
* выполнение в привилегированном режиме

---

### Почему драйверы работают в kernel space

Работа с аппаратным обеспечением требует:

* прямого доступа к портам ввода-вывода
* управления прерываниями
* работы с физической памятью
* выполнения привилегированных инструкций CPU

Все перечисленные операции доступны только в режиме ядра.

Ключевая идея:

> Драйвер работает в kernel space, потому что только ядро имеет право напрямую взаимодействовать с оборудованием.

---

### Последствия работы в kernel space

Поскольку драйвер выполняется в пространстве ядра:

* ошибка в драйвере может привести к сбою всей системы
* драйвер имеет доступ ко всей памяти
* некачественный драйвер — одна из наиболее частых причин нестабильности ОС

Исторический факт:

> Согласно исследованиям Microsoft, около 85% аварийных завершений Windows в своё время были вызваны ошибками в
> сторонних драйверах.

---

## Типы устройств и типы драйверов

### Типы устройств

#### Блочные устройства

Устройства, работающие с данными блоками фиксированного размера.

Примеры:

* жёсткие диски
* SSD
* USB-накопители

Особенности:

* данные адресуются по номеру блока
* поддерживается произвольный доступ
* операции чтения и записи выравниваются по границе блока

---

#### Символьные устройства

Устройства, работающие с данными как с потоком байтов.

Примеры:

* клавиатуры
* мыши
* последовательные порты (UART, USB Serial)
* терминалы

Особенности:

* данные читаются и записываются последовательно
* произвольный доступ, как правило, не поддерживается
* взаимодействие через поток

---

#### Сетевые устройства

Устройства, обеспечивающие сетевое взаимодействие.

Примеры:

* сетевые карты (Ethernet)
* Wi-Fi адаптеры

Особенности:

* работают с пакетами данных
* не представлены в `/dev` как файлы
* управляются через сетевой стек ОС

---

### Типы драйверов

#### Монолитные драйверы

Встроены непосредственно в ядро операционной системы.

Особенности:

* загружаются вместе с ядром при старте
* не могут быть выгружены без перезагрузки
* используются для критически важных компонентов

---

#### Загружаемые модули ядра

Драйверы, которые могут быть загружены и выгружены динамически без перезагрузки системы.

Особенности:

* загружаются по требованию
* снижают размер базового ядра
* позволяют добавлять поддержку устройств без пересборки ядра

Пример:

* подключение USB-устройства → автоматическая загрузка модуля

---

#### Драйверы пространства пользователя

Специальный класс драйверов, выполняющихся в user space.

Особенности:

* ограниченный доступ к оборудованию
* более безопасны — ошибка не обрушивает систему
* используются для определённых классов устройств (например, принтеры через CUPS)

---

### Практическая демонстрация

#### Блочные и символьные устройства в системе

```bash

ls -l /dev | grep "^c"   # символьные
```

Анализ:

* первый символ в правах доступа: `b` — блочное, `c` — символьное
* примеры устройств каждого типа

---



Анализ:

## Драйверы и файловая система

### Каталог /dev

В системах семейства Unix устройства представлены как специальные файлы в каталоге `/dev`.

Примеры:

* `/dev/sda` — первый диск
* `/dev/sda1` — первый раздел первого диска
* `/dev/tty` — текущий терминал
* `/dev/null` — «чёрная дыра» (всегда принимает данные, ничего не возвращает)
* `/dev/random` — генератор случайных чисел

Ключевая идея:

> Работа с устройством осуществляется теми же системными вызовами, что и работа с обычным файлом: `open()`, `read()`,
`write()`, `close()`.

---

### Связь с VFS

Каталог `/dev` интегрирован в виртуальную файловую систему (VFS).

Схема взаимодействия:

```text
open("/dev/sda")
↓
VFS
↓
Драйвер блочного устройства
↓
Физический диск
```

Следствие:

> Приложение не знает и не должно знать, с чем именно оно работает — с файлом на диске или с устройством. Интерфейс
> одинаков.

---

### Специальные файлы устройств

Файлы устройств содержат не данные, а идентификаторы:

* **major number** — идентифицирует драйвер
* **minor number** — идентифицирует конкретное устройство среди обслуживаемых этим драйвером

Пример:

```text
brw-rw---- 1 root disk 8, 0 /dev/sda
brw-rw---- 1 root disk 8, 1 /dev/sda1
```

Здесь `8` — major number (драйвер дисков), `0` и `1` — minor numbers.

---

### udev и динамическое управление устройствами

В современных Linux-системах каталог `/dev` формируется динамически с помощью **udev**.

Принцип работы:

* ядро обнаруживает устройство и генерирует событие
* udev получает событие
* udev создаёт соответствующий файл в `/dev`
* при отключении устройства файл удаляется

Следствие:

> Подключение USB-накопителя автоматически порождает файл `/dev/sdb` без перезагрузки системы.

---

### Практическая демонстрация

#### Просмотр файлов устройств

```bash

```

Анализ:

* типы файлов (`b`, `c`)
* major и minor числа

---


```bash

```

Анализ:

---

#### Взаимодействие с устройством как с файлом

```bash

```

Обсуждение:

* `/dev/null` принимает любые данные
* чтение из него возвращает пустой результат
* это устройство, но интерфейс идентичен файловому

---

#### Отслеживание событий устройств (при наличии прав)

Linux:

```bash

```

Действие:

* подключить и отключить USB-накопитель

Наблюдение:

* события появления и удаления устройства
* создание и удаление файла в `/dev`

## Загрузка и управление драйверами

### Статическая загрузка

Некоторые драйверы встроены в ядро и загружаются вместе с ним при загрузке системы.

Характеристики:

* всегда присутствуют в памяти
* не могут быть выгружены
* используются для базовых компонентов (например, драйверы файловых систем)

---

### Динамическая загрузка (модули ядра)

В Linux драйверы могут быть оформлены как загружаемые модули ядра (`.ko` — kernel object).

Преимущества:

* ядро не перегружается лишними драйверами
* поддержка новых устройств добавляется без пересборки ядра
* модуль можно выгрузить, освободив ресурсы

---

### Автоматическая загрузка

Современные системы загружают драйверы автоматически при обнаружении устройства.

Механизм:

* устройство подключается к шине (USB, PCI)
* ядро получает идентификатор устройства (vendor ID, device ID)
* ядро ищет подходящий модуль в базе данных
* модуль загружается автоматически

---

### Основные команды управления модулями (Linux)

| Команда                | Описание                   |
|------------------------|----------------------------|
| `lsmod`                | список загруженных модулей |
| `modinfo <модуль>`     | информация о модуле        |
| `modprobe <модуль>`    | загрузить модуль           |
| `modprobe -r <модуль>` | выгрузить модуль           |
| `insmod <файл.ko>`     | загрузить модуль из файла  |
| `rmmod <модуль>`       | выгрузить модуль           |

---

### Управление драйверами в macOS

В macOS расширения ядра называются **kext** (kernel extension).

Основные команды:

```bash
kextstat                        # список загруженных расширений
kextstat | grep -v com.apple    # сторонние расширения
```

Начиная с macOS 11:

* Apple переходит на **DriverKit** — драйверы в user space
* повышает стабильность и безопасность системы

## Безопасность и стабильность

### Угрозы стабильности

Ошибки в драйвере могут привести к:

* **Kernel panic** (Linux) / **Blue Screen of Death** (Windows) — аварийное завершение работы ядра
* зависанию системы
* повреждению данных
* некорректной работе других компонентов

Причина:

> Ядро не имеет механизма изоляции от ошибок драйвера — они выполняются в одном адресном пространстве.

---

### Угрозы безопасности

Вредоносный или скомпрометированный драйвер получает:

* полный доступ к памяти всех процессов
* возможность перехвата любых данных
* возможность обхода любых механизмов защиты

Такой класс вредоносного ПО называется **rootkit**.

---

### Механизмы защиты

#### Подписание драйверов

Современные ОС требуют криптографической подписи драйверов.

Linux:

* опциональная проверка подписи модулей (Secure Boot)

macOS:

* обязательная подпись kext
* начиная с macOS 10.15: предупреждение при установке сторонних kext
* начиная с macOS 11: рекомендован переход на DriverKit

Windows:

* обязательная подпись с 64-битных версий Windows Vista

---

#### Изоляция драйверов в user space

Современная тенденция — перенос части драйверов в пространство пользователя.

Преимущества:

* ошибка в драйвере не обрушивает систему
* ограниченный доступ к ресурсам

Примеры:

* macOS DriverKit
* FUSE (Filesystem in Userspace) в Linux

---

#### Проверка целостности ядра

Linux:

* **Kernel Lockdown** — ограничение возможностей модулей при включённом Secure Boot

macOS:

* **System Integrity Protection (SIP)** — защита системных компонентов от модификации

---

### Практическая демонстрация

#### Проверка подписи модулей

Linux:

```bash
cat /proc/sys/kernel/modules_disabled
```

macOS:

```bash

```

Анализ:

* статус защиты системы
* ограничения на загрузку модулей

---

#### Журнал ошибок драйверов

Linux:

```bash

```

macOS:

```bash

```

Анализ:

* сообщения об ошибках
* предупреждения при загрузке модулей

## Разработка драйвера (обзорно)

### Общая характеристика

Разработка драйвера — это разработка кода, работающего в пространстве ядра. Это принципиально отличается от написания
обычных приложений: нет стандартной библиотеки C, нет защиты от segfault, ошибка — это потенциальный сбой всей системы.

---

### Модуль ядра Linux

Простейший драйвер в Linux — это **загружаемый модуль ядра**.

Минимальный модуль состоит из двух функций:

* функция инициализации — вызывается при загрузке модуля
* функция очистки — вызывается при выгрузке модуля

---

### Пример: минимальный модуль ядра

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Student");
MODULE_DESCRIPTION("Minimal kernel module example");

static int __init hello_init(void)
{
    printk(KERN_INFO "Driver loaded: hello from kernel space\n");
    return 0;
}

static void __exit hello_exit(void)
{
    printk(KERN_INFO "Driver unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
```

---

### Разбор кода

**`#include <linux/module.h>`** — заголовки ядра, не стандартной библиотеки C.

**`MODULE_LICENSE("GPL")`** — лицензия модуля. Ядро Linux требует совместимой лицензии для доступа к части API.

**`printk()`** — аналог `printf()` для ядра. Вывод идёт в журнал ядра (`dmesg`), а не в терминал.

**`__init` и `__exit`** — атрибуты, подсказывающие ядру, что эти функции можно выгрузить из памяти после использования.

**`module_init()` / `module_exit()`** — макросы, регистрирующие функции инициализации и очистки.

---

### Что происходит при загрузке модуля

```text
sudo insmod hello.ko
↓
Ядро проверяет модуль (версия, подпись)
↓
Ядро вызывает hello_init()
↓
Сообщение появляется в dmesg
↓
Модуль находится в памяти и готов к работе
```

---

### Чем драйвер отличается от обычной программы

| Обычная программа               | Драйвер (модуль ядра)       |
|---------------------------------|-----------------------------|
| User space                      | Kernel space                |
| Стандартная библиотека C        | API ядра                    |
| Segfault → завершение программы | Segfault → kernel panic     |
| Изолирован от других процессов  | Имеет доступ ко всей памяти |
| `printf()`                      | `printk()`                  |
| `malloc()`                      | `kmalloc()`                 |

---

### Куда двигаться дальше

Реальный драйвер устройства дополнительно реализует:

* регистрацию устройства в системе
* обработку операций `open`, `read`, `write`, `ioctl`
* обработку прерываний
* управление памятью устройства

---

```bash
ls /dev/cu.*
```

Linux:

```bash
ls /dev/ttyUSB* /dev/ttyACM*
```

Наблюдение:

* появился новый файл устройства
* ОС автоматически обнаружила устройство и создала файл в `/dev`

### Шаг 2. Какой драйвер обслуживает устройство

#### Сообщения ядра при подключении

macOS:

```bash
log show --last 1m | grep -i usb
```

Linux:

```bash
dmesg | tail -20
```

Анализ:

* ядро определило устройство по USB идентификатору
* загружен драйвер последовательного порта (`ch341` или `cp210x` для Linux, встроенный CDC для macOS)
* создан файл устройства

### Шаг 3. Взаимодействие с устройством

Arduino — это символьное устройство, работающее как последовательный порт. Взаимодействие осуществляется через
стандартный файловый интерфейс.

#### Подключение через стандартный терминальный инструмент

macOS:

```bash
screen /dev/cu.usbserial-XXXX 9600
```

Linux:

```bash
screen /dev/ttyUSB0 9600
```

Отправка команды:

```text
ON
```

Наблюдение:

* светодиод включился
* Arduino ответила подтверждением

Ключевой момент:

> `screen` — это обычная программа, которая открывает файл устройства через `open()` и читает из него через `read()`.
> Никакого специального API для работы с Arduino не требуется.

---

### Шаг 4. Взаимодействие без специальных инструментов

Поскольку устройство представлено как файл, с ним можно взаимодействовать напрямую.

```bash
echo "ON" > /dev/cu.usbserial-XXXX
```

```bash
echo "OFF" > /dev/cu.usbserial-XXXX
```

Наблюдение:

* стандартная команда `echo` управляет физическим светодиодом
* никакого специального кода не потребовалось

---

### Итог демонстрации

```text
echo "ON" > /dev/cu.usbserial-XXXX
↓
Системный вызов write()
↓
VFS
↓
Драйвер последовательного порта (kernel space)
↓
USB контроллер
↓
Arduino Nano
↓
Светодиод включился
```

Именно этот путь проходит каждая команда при взаимодействии с любым устройством в Unix-системе.
